## Remaining issues and tradeoffs

- **Workspace ownership remains advisory at the API write boundary.**
  `server.py` accepts authenticated workspace PUTs without verifying the writer's
  registry identity or a document revision. The serialization added here prevents
  overlapping writes from finishing in reverse order, but cannot reject a stale
  client that submits an old layout later. Enforcing ownership or optimistic
  revisions server-side would require a coordinated API/client change, including
  dashboard edits to workspaces open elsewhere.
- **UI coordination is concentrated in `main.js`.** It owns launch requests,
  saves, workspace transitions, session membership, and window registration.
  Extracting a workspace controller would make lifecycle behavior easier to
  exercise directly. Many existing frontend Python tests assert source strings
  rather than executing interactions; those are useful contracts but cannot
  establish that the rendered app works.
- The second view uses another same-origin document and therefore another set
  of UI resources and terminal connections. Hidden views intentionally remain
  alive. The second view is optional, limited to one, and is not automatically
  restored at startup. Its terminal splits remain ordinary saved layouts.
- Only named workspaces are offered when initially opening beside the primary
  view. Each view retains its existing workspace selector, so switching remains
  available. A workspace claimed by another viewer cannot be opened twice.
